## 四、API 規格

> 目前**沒有**自動產生的 API 文件（如 Swagger），這裡記錄**約定慣例**，實際欄位請直接看對應 `*.controller.ts` / `*.dto.ts`。歷史上各 Phase 新增的端點清單可在 `04 開發進度 updated.md` 各 Phase 段落查到（例如 Phase 7 監控系統列出的 `GET /monitoring/orders` 等）。

### 4.1 路由慣例

```
所有 API 皆有 /api 前綴（由 Nginx 在正式環境加上，NestJS 本身不帶前綴）
backend/src/<module>/<module>.controller.ts   定義路由
backend/src/<module>/<module>.service.ts      定義商業邏輯
backend/src/<module>/dto/                     定義輸入驗證（class-validator）
```

常見端點命名模式（以「進貨」模組為例，其他作業系統模組同構）：
```
GET    /receiving/orders                列表（支援 query 篩選）
GET    /receiving/orders/:id            單一主單明細（支援 ?includeDeleted=true）
POST   /receiving/orders                新建主單
PATCH  /receiving/orders/:id            更新主單（如修改日期）
DELETE /receiving/orders/:id/soft       軟刪主單
DELETE /receiving/orders/:id/hard       硬刪主單（ADMIN only，寫 AuditLog）

POST   /receiving/details               新建明細
PATCH  /receiving/details/:id           更新明細
DELETE /receiving/details/:id/soft      軟刪明細
DELETE /receiving/details/:id/hard      硬刪明細（ADMIN only）
```
> 各模組實際路徑、動詞、是否走 soft/hard 兩段式不完全一致，**新增功能前務必先看該模組現有 controller 確認既有慣例**，不要自己發明新模式。

### 4.2 權限慣例

```
@UseGuards(JwtAuthGuard, RolesGuard)
@Roles('ADMIN', 'OFFICE')   // 範例：僅 ADMIN/OFFICE 可呼叫
```
角色繼承關係（見 00 總覽）：ADMIN 可做所有事；OFFICE 可做主資料+進貨+報表，不可碰現場加工流程；FACTORY 可做加工但不可碰主資料；GUIDED 僅能用導引式介面操作被指派流程。

**軟刪 vs 硬刪權限**（全系統統一規則）：
```
軟刪：ADMIN + OFFICE 皆可
硬刪：僅 ADMIN（且後端會擋掉「刪除自己帳號」這類危險操作，使用者管理模組為例）
```

### 4.3 圖片上傳

```
上傳端點：multipart/form-data，由 @fastify/multipart 處理（10MB 上限）
實際檔案寫入：backend/public/uploads/<uuid>.<ext>
靜態存取路徑：/uploads/<filename>（由 backend/src/main.ts 的 fastify-static 提供，root 指向 backend/public）
資料庫只存檔名（imageUrl 欄位），不存完整 URL
```
⚠️ **VPS 正式環境的 Nginx 必須額外設定 `/uploads/` 轉發規則**，否則圖片會破圖（詳見本手冊「常見維修流程 → 圖片上傳後顯示破圖」）。

### 4.4 金額計算

```typescript
// 唯一合法寫法，一律在 Service 層算
const amount = Math.floor(Number(qty) * Number(rate))
```
禁止在前端算金額後傳給後端存；前端只負責顯示、後端 Service 層才是金額計算的唯一真相來源。

## 五、部署流程

### 5.1 標準部署指令（日常使用）

```powershell
# 本機
cd C:\yowthi-erp
git add -A
git commit -m "說明這次改了什麼"
git push vps master
```
```powershell
# VPS（透過 SSH，固定指令，含清除 lockfile 衝突）
ssh -i $env:USERPROFILE\.ssh\id_ed25519 -o StrictHostKeyChecking=no root@162.141.142.147 "cd /var/www/yowthi-erp && git checkout -- frontend/package-lock.json backend/package-lock.json 2>/dev/null; ./deploy.sh 2>&1"
```

`deploy.sh` 會自動依序執行：`git pull` → backend build → frontend build → `prisma generate` → `pm2 restart` → 印出 log。

### 5.2 為什麼一定要走 `git push` + `deploy.sh`，不能手動改 VPS 上的檔案

歷史上發生過「只上傳 `src/` 原始碼，沒重新 `npm run build`」導致 VPS 跑的是舊編譯結果（見 04 開發進度 Phase 9.x），花了很大代價才查出來並重建整個部署機制。**現在唯一被信任的部署路徑就是上面這兩條指令**，任何「手動改 VPS 上的檔案」都視為臨時除錯手段，事後必須把同樣的改動透過 git 補回來，否則下次 `git pull` 會被覆蓋回舊版本。

### 5.3 Schema 變更時的額外步驟

如果這次修改了 `backend/prisma/schema.prisma`：
1. `deploy.sh` 執行時只會「提醒」有 schema 變更，**不會自動跑 migration**
2. 需要額外 SSH 進 VPS 手動執行（依情況選一個）：
   ```bash
   cd /var/www/yowthi-erp/backend
   npx prisma db push          # 開發/小變更，不留 migration 歷史
   # 或
   npx prisma migrate deploy   # 正式 migration（建議優先使用，留歷史紀錄）
   ```
3. 再重新 `pm2 restart yowthi-backend`

### 5.4 VPS 基礎設施相關（不在 git 版控內，需要另外記住）

以下幾項**不屬於程式碼**，git 部署不會自動處理，需要單獨留意：
- **Nginx 設定** (`/etc/nginx/sites-enabled/default`)：HTTPS server block 目前包含 `/api/`、`/uploads/`（2026-06-27 補上）兩條 proxy_pass 規則 + SPA fallback。未來如果新增其他需要直接代理到 backend 的路徑（例如未來可能的 WebSocket、檔案下載端點），記得同步加 Nginx 規則
- **`backend/public/uploads/`**：使用者上傳的圖片實體檔案，是「使用者資料」不是程式碼，沒有自動備份機制，建議定期手動備份（`scp` 整個資料夾回本機或另存雲端）
- **PM2 process**：`ecosystem.config.js` 已納入版控，但 `pm2 save`（讓 PM2 開機自動啟動）狀態不在 git 裡，VPS 重啟後若 PM2 沒自動啟動需要手動 `pm2 resurrect` 或重新 `pm2 start ecosystem.config.js && pm2 save`
- **`.env` 檔案**：兩邊 `.env`（`backend/.env`）皆被 `.gitignore` 排除，不在版控內，VPS 上的 `.env` 是獨立維護的，內含 `DATABASE_URL` / `JWT_SECRET` / `JWT_EXPIRES_IN`，**修改前務必先備份一份**

## 六、Git 規範

### 6.1 基本約定
- 單一分支 `master`，沒有 feature branch 流程（專案規模小，個人開發為主）
- Commit message 用繁體中文，簡短描述「做了什麼」，可以一次 commit 包含多項小修正（用分號隔開），不需要嚴格遵守 Conventional Commits 格式
- VPS 端的 git remote 是 bare repo（`/root/yowthi-erp.git`），本機 push 上去之後，VPS 工作目錄要另外 `git pull`（由 `deploy.sh` 處理）

### 6.2 `package-lock.json` 衝突的標準處理

**現象**：VPS 上 `npm install`／build 過程會更新 `frontend/package-lock.json`、`backend/package-lock.json`，造成這兩個檔案在 VPS 工作目錄裡跟 git 歷史不一致，下次 `git pull` 會衝突失敗。

**標準處理**：部署指令固定在 `git pull`／`deploy.sh` 之前加一行：
```bash
git checkout -- frontend/package-lock.json backend/package-lock.json 2>/dev/null
```
等於是「VPS 上這兩個 lockfile 的本地異動不重要，永遠以 git 版本為準，先還原再 pull」。**這條指令已經是每次部署的固定動作，不要省略。**

> 未來優化方向（尚未實作）：把這兩個 lockfile 加進 VPS 端的 `.git/info/exclude`，讓 git 直接忽略它們在 VPS 上的異動，不用每次手動還原。

### 6.3 `.gitignore` 現狀

```
根目錄：node_modules / .env / dist
backend：node_modules / .env / /generated/prisma
```
⚠️ **注意**：`backend/public/uploads/`（使用者上傳圖片）目前**沒有**被 gitignore，理論上會被 git 追蹤，但實務上使用者直接在正式環境上傳的圖片不會經過「本機 commit」這個流程，所以不能假設正式環境的上傳圖片有被版控保護到。如果要讓上傳圖片真正受版控保護，需要額外排程或腳本去同步。

## 七、AI 工作規範

> 開發規則的「強制嚴守」清單（不可跳 Phase、每次對話結尾要回報完成項目等）已寫在 [`00_專案總覽.md`](./00_專案總覽.md) 的「開發規則」一節，這裡補充的是**實際協作流程中發現的操作細節**，00 總覽沒有涵蓋。

### 7.1 雙 AI 協作模式

本專案同時使用兩個 AI 工具，分工方式：
- **Claude（網頁/App 對話）**：負責規格討論、程式碼撰寫/編輯（透過檔案系統工具直接讀寫 `C:\yowthi-erp` 下的檔案）、問題診斷、產出要貼給 Claude Code 執行的指令
- **Claude Code（VS Code 終端機）**：負責實際執行 git/SSH/部署指令、跑 VPS 上的維運指令（因為它有終端機與 SSH 金鑰存取權，Claude 網頁版沒有）

協作流程：Claude 寫好程式碼變更 → 把對應的 git/SSH 指令整理好給使用者 → 使用者貼到 Claude Code → Claude Code 詢問確認後執行 → 把執行結果截圖回給 Claude 確認。

### 7.2 已知的工具層注意事項

- **Claude Code 對 PowerShell 指令的誤判**：執行帶有 `$env:USERPROFILE` 這類 PowerShell 變數語法的 SSH 指令時，Claude Code 偶爾會跳出 `zsh $name[expr] / $name:mod in bare concatenation` 這類警告，這是它把 PowerShell 語法誤判為 zsh 特殊語法，**實際指令沒有問題**，正常選 Yes 繼續執行即可
- **PowerShell 字串跳脫地雷**：含 `$` 符號的字串（例如 bcrypt hash `$2b$10$...`）透過 SSH 指令直接傳遞時，會被本機 PowerShell 當成變數展開，導致內容被截斷。安全做法：先寫入本機暫存檔，再用 `scp` 二進位傳輸，不要把含 `$` 的內容直接塞進 SSH 指令字串裡
- **psql 連線方式**：VPS 上直接用 `psql` 預設走 peer authentication 會失敗，要用 `sudo -u postgres psql ...`
- **`DROP DATABASE` 被佔用**：如果有連線中的 session，要先 `pg_terminate_backend` 清空連線才能 DROP

### 7.3 給 Claude（本體）的維護提醒

- 修改 Vue 元件前，**務必先讀完整個檔案**，確認既有的 class 命名、i18n key、按鈕風格慣例，不要憑空套用「自己覺得合理」的新樣式（本手冊「常見維修流程」記錄過好幾次因為各模組風格不一致導致的返工）
- 任何**共用工具檔**（`pdfExport.ts`、`shareExport.ts`、`offlineDb.ts` 等）的改動會影響全部引用它的模組，修改前要先確認影響範圍（搜尋所有 import 該檔案的地方），改完也要提醒使用者「這次影響哪些頁面」
- 處理「手機版排版問題」時，預設假設是**沒有 `overflow-x: auto` + `min-width` 保護**造成的硬擠壓，這是本專案重複出現過最多次的同類 bug 模式
- 工具連線（filesystem MCP）有時會在對話中途斷線或降級成唯讀，遇到工具消失時嘗試重新呼叫載入工具的指令，如果還是不行，改為產出「貼給 Claude Code 執行」的明確指令，不要乾等

## 八、常見維修流程

### 8.1 登入卡死、畫面停在「登入中」不回應

**先檢查**：是否剛好是「部署完新版本後馬上開啟 App」的情境？
- 是 → 大概率是 PWA Service Worker 在背景更新搶網路（2026-06-27 已修正為 `registerType: 'prompt'` + 延後註冊，理論上不會再發生，但如果客戶手機上是更早裝的 PWA、舊版 SW 邏輯還沒換掉，仍可能發生一次，重新開啟一次 App 即可恢復）
- 不是 → 檢查 VPS 即時狀態（卡住的當下立刻執行，不要等使用者重新整理）：
  ```bash
  pm2 logs yowthi-backend --lines 80 --nostream
  tail -80 /var/log/nginx/error.log
  tail -30 /var/log/nginx/access.log
  pm2 status
  ```
  重點看 access log 裡卡住那個時間點的請求是否真的有回應、回應碼是什麼。axios 已設定 15 秒逾時（`main.ts`），超過會自動報錯而不會永久卡死。

### 8.2 圖片上傳後顯示破圖

**先檢查上傳的檔案是否真的寫進伺服器**：
```bash
ls -la /var/www/yowthi-erp/backend/public/uploads/ | tail -10
```
- 檔案不存在 → 後端儲存邏輯有問題，檢查 `backend/src/main.ts` 的 `@fastify/multipart` 設定跟對應 controller 的上傳處理
- 檔案存在但前端還是破圖 → 檢查 Nginx 設定是否有 `/uploads/` 的 proxy_pass 規則（2026-06-27 發生過從建站以來就漏掉這條規則，詳見「五、部署流程」與「四、API規格」相關段落）：
  ```bash
  cat /etc/nginx/sites-enabled/default
  ```
  確認有：
  ```nginx
  location /uploads/ {
      proxy_pass http://127.0.0.1:3000/uploads/;
  }
  ```
  且這條規則在 SPA fallback（`location /`）**之前**。改完 `nginx -t && systemctl reload nginx`。

### 8.3 手機窄螢幕排版跑掉／橫向被撐開／需要左右滑動才看得到按鈕

最常見原因：某個 flex 容器設了 `flex-wrap: nowrap`，或表格用 grid 固定欄寬卻沒給 `overflow-x: auto` + `min-width`。

排查方式：
1. 找到對應 `.vue` 檔案的 `<style scoped>`
2. 搜尋 `flex-wrap: nowrap` → 改成 `wrap`（如果是按鈕/標籤類內容，允許換行通常是安全的）
3. 如果是多欄表格（`display: grid` + 多個 `fr` 欄位），確認外層容器有 `overflow-x: auto`，且 `.row` 有設 `min-width`（沒設的話手機會把欄位硬擠壓而不是滑動）

### 8.4 部署後功能沒生效（程式碼明明改了，VPS 行為卻沒變）

依序排查：
1. 本機是否真的 `git push vps master` 成功（看有沒有報錯）
2. VPS 是否真的跑了 `./deploy.sh`（不能只 `git pull` 不 build）
3. `deploy.sh` 的 build 步驟有沒有報錯（看 `frontend build` / `backend build` 那兩步輸出）
4. `pm2 restart` 之後 `pm2 logs yowthi-backend --lines 30` 確認 `Nest application successfully started`，且沒有殘留舊 process（`pm2 status` 確認只有一個 `yowthi-backend`，沒有重複或多個 PID）
5. 前端如果還是舊版：請使用者**完全關閉分頁重開**（不是單純重新整理），因為 PWA Service Worker 是 `prompt` 模式，新版本要等下次完整重開才會套用（見「七、AI工作規範」與 04 開發進度 Phase 8.x (F) 段落）

### 8.5 硬刪除失敗、或刪除後出現外鍵錯誤

全系統硬刪都已經統一處理 Prisma `P2003`/`P2014` 外鍵約束錯誤，轉成 HTTP 409 並回傳清楚訊息（見 04 開發進度 Phase 6.7）。如果遇到刪除失敗：
1. 看前端錯誤訊息是不是「409 + 說明文字」（正常情況，代表這筆資料還被其他單據關聯，本來就不該刪）
2. 如果是「500 + 看不懂的錯誤」，代表某個較新模組的 hardDelete 函式漏補這層保護，需要照其他模組的寫法（`try { await prisma.xxx.delete(...) } catch (e) { if (e.code === 'P2003' || e.code === 'P2014') throw new ConflictException(...) }`）補上去

### 8.6 新增一個查詢頁面的 PDF 匯出/分享功能

直接複製任何一個現有查詢頁面（例如 `ReceivingInquiryView.vue`）的 `buildPdfOptions()` / `exportPdf()` / `sharePdf()` 三個函式當模板，**不要自己重新發明**：
- PDF 排版（直式/橫式、字級）由共用工具 `pdfExport.ts` 統一控制，目前固定全部直式，不需要在頁面層處理方向
- 分享功能用 `shareExport.ts` 的 `sharePdfBlob()`，不需要處理 `navigator.share` 細節
- 「分享圖片至LINE」功能目前**只有員工薪資查詢有試裝**，其他頁面預設沒有這顆按鈕（刻意決定，因為截圖功能比較容易在不同手機上出狀況，見 04 開發進度 Phase 8.x (A) 段落的踩雷記錄），如果要加到其他頁面，記得套用同一套 `windowWidth` 截圖機制，不要自己改用直接修改 DOM 樣式的方式（會在三星手機黑屏）
