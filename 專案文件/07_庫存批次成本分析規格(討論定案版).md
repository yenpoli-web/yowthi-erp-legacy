# 庫存批次生產成本分析 + 包裝模組改版 — 規格定案文件

> 狀態：討論定案，待確認後實作
> 日期：2026-06-29
> 背景：原成本分析模組（資料查詢 → 成本分析）採「銷售單事後追溯進貨單」的設計，
> 發現同一批入庫被分次銷售時會有「重複計算」或「漏算」的兩難，且無法同時滿足
> 「單獨查任何一張銷售單都得到一致數字」與「合併查不會重複計算」兩個需求——
> 這兩個需求只有「比例分攤（單位成本法）」在數學上能同時滿足。
> 故重新設計：成本改在「入庫批次」這一刻就鎖定，銷售單只需「數量 × 鎖定的單位成本」。

-----

## 一、核心結論：分析單位 = 進貨單（ReceivingOrder）

**關鍵 schema 事實**（已查證）：
- `ProcessingOrder`（加工單）以 `orderDate`（加工日期）+ `receivingItemId`（進貨品項）為唯一鍵，
  **不綁定特定一張進貨單**。同一張加工單的明細，可能來自不同天的不同進貨單。
- 但每一筆 `ProcessingDetail` 明細都明確記錄了來源：
  - H01：透過 `batchId` → `ReceivingBatch.orderId` → 特定進貨單
  - H02/H03：直接有 `receivingOrderId` → 特定進貨單

**結論**：「加工單」不是乾淨的成本單位（可能混雜多張進貨單），**「進貨單」才是唯一乾淨、可追溯的分析單位**。
聚合方式 = 抓出所有 `ProcessingDetail`（不管屬於哪張加工單）裡 `receivingOrderId`（或 H01 透過 batch 間接）
等於該進貨單的明細，加總其 H01+H02 金額與 H02 產出重量。

這跟現有「進貨加工監控」模組的聚合邏輯完全一致，可以直接沿用其查詢邏輯。

-----

## 二、新模組：庫存批次生產成本分析

**位置**：作業系統內新增模組（不是資料查詢），因為其結果需要「鎖定」並提供給入庫流程使用，
屬於「進貨→加工→入庫→銷售」作業鏈的前置步驟。

### 分析對象
以「進貨單」為單位，僅限 `h02Done = true`（H02 加工已全部完成標記）的進貨單才能進行鎖定
（與現有入庫畫面「需 H02 加工完成」的限制一致，確保鎖定時基數已經穩定）。

### 三個成本欄位（每公斤）

| 欄位 | 內容 | 鎖定時機 |
|---|---|---|
| 欄位1：基礎成本 | (該進貨單下 H01+H02 加工金額加總) ÷ (該進貨單下 H02 完成品總重量) | 使用者按下「鎖定」當下 |
| 欄位2：預估成本（含包裝） | 欄位1 + 預估包裝成本／公斤 | 同上，鎖定時一併估算，僅供定價參考 |
| 欄位3：真實成本（含包裝） | 欄位1 + 實際包裝成本／公斤（依該進貨單實際登錄的 K01/K02/K04 包裝明細金額 ÷ H02完成品總重量） | **不鎖定**，隨包裝明細登錄即時更新（因為包裝可能晚於入庫才完成登記） |

**欄位2 需要兩個附帶輸入欄位**（手動填入，沒有數量就無法估算）：
```
預估籃子數量（estBasketQty）：整數，手動輸入
預估箱子數量（estBoxQty）：整數，手動輸入

預估包裝成本／公斤 = (預估籃子數量 × 80 + 預估箱子數量 × 40) ÷ 該進貨單 H02 完成品總重量
欄位2 = 欄位1 + 預估包裝成本／公斤
```
這兩個欄位是「使用者依經驗判斷這批貨大概要用多少籃子/箱子」自行填入的估計值，
跟欄位3「實際登錄的包裝明細」是兩條獨立的數字（欄位2鎖定後不變，欄位3持續依實際登錄更新），
讓使用者在還沒真正包裝之前，就能先抓一個估計成本來決定定價。

**鎖定後不再變動**：欄位1、欄位2 鎖定後即固定，即使後續發現該進貨單的加工或包裝有異動，也不會自動重算
（若真的需要修正，需要管理者手動「解除鎖定」重新計算，這個功能視需求後續再評估是否要做）。
欄位3 是唯一持續更新的欄位（因為包裝本來就可能分批登錄、晚於入庫完成）。

### 鎖定後的應用
- **成品入庫**畫面：選擇來源進貨單時，自動帶入該批已鎖定的「欄位1」單位成本，
  入庫單價欄位**不再手動輸入**，畫面只剩數量處理。
- 入庫明細的 `unitPrice`／`amount` 直接套用鎖定值 × 入庫數量／重量。

## 三、包裝模組改版

### PackagingItem 新增欄位
```
applicableTo: 'RECEIVING_ORDER' | 'SALES_ORDER'   (新增 enum 欄位，新建項目時設定一次)
```

### 既有四個包裝項目對應（2026-07-04 更正）

| 項目 | 適用對象 | 數量基準 |
|---|---|---|
| K01 裝籃 ใส่ตะกร้า（工資80） | RECEIVING_ORDER | 籃子數 |
| K02 裝箱 ใส่กล่อง（工資40） | RECEIVING_ORDER | 箱子數 |
| K03 出貨包裝 แพ็คของส่งออก | SALES_ORDER | 維持現狀 |
| K04 收集檳榔葉 รวบรวมใบพลู（工資1） | SALES_ORDER | 重量（kg） |

> **2026-07-04 更正**：K04 原定案為 RECEIVING_ORDER，經使用者確認後更正為 **SALES_ORDER**。目前只有 K01、K02 對應進貨單，K03、K04 對應銷售單。「庫存批次生產成本分析」欄位3（真實成本）的包裝金額加總也同步只計入 K01/K02，程式碼已改為一律讀 `PackagingItem.applicableTo` 動態判斷（不再硬編 ID 清單），避免下次再有類似調整需求時漏改。

### PackagingDetail 新增欄位
```
receivingOrderId: String?   (RECEIVING_ORDER 類型用，新增)
salesOrderId 已存在於 PackagingOrder 層級，SALES_ORDER 類型沿用現狀，不變動
```

> 注意：現有 `salesOrderId` 是掛在 `PackagingOrder`（主單）上，但 `receivingOrderId` 應該掛在
> `PackagingDetail`（明細）還是 `PackagingOrder`（主單）需要再確認——若一張包裝主單下的不同明細
> 可能對應不同進貨單，應掛在明細層級；若一張包裝主單固定對應一張進貨單，可掛在主單層級，
> 與現有 `salesOrderId` 的掛法一致。**這點待實作前再次確認**。

### 新建包裝明細流程
依 `PackagingItem.applicableTo` 自動決定導引流程：
- `RECEIVING_ORDER` 類型 → 跳出「選取進貨單」（TouchSelectorModal，沿用進貨單選取邏輯）
- `SALES_ORDER` 類型 → 跳出「選取銷售單」（維持現狀）

使用者選好包裝項目後，系統自動判斷該走哪種流程，不需要每次手動選擇類型。

## 四、Schema 變更總覽

```prisma
enum PackagingApplicableTo {
  RECEIVING_ORDER
  SALES_ORDER
}

model PackagingItem {
  // ...existing fields...
  applicableTo PackagingApplicableTo @default(SALES_ORDER)  // 新增
}

model PackagingDetail {
  // ...existing fields...
  receivingOrderId String?         // 新增
  receivingOrder   ReceivingOrder? @relation(fields: [receivingOrderId], references: [id])  // 新增
}

model ReceivingOrder {
  // ...existing fields...
  costLocked        Boolean   @default(false)              // 新增：是否已鎖定生產成本
  costUnitPrice      Decimal? @db.Decimal(12, 2)            // 新增：欄位1 基礎成本/kg
  costUnitPriceEst   Decimal? @db.Decimal(12, 2)            // 新增：欄位2 預估成本/kg（含預估包裝）
  costEstBasketQty   Int?                                   // 新增：欄位2 預估籃子數量（手動填入）
  costEstBoxQty      Int?                                   // 新增：欄位2 預估箱子數量（手動填入）
  costLockedAt       DateTime?                              // 新增：鎖定時間
  costLockedBy       Int?                                   // 新增：鎖定操作人（User.id）
  packagingDetails   PackagingDetail[]                       // 新增 relation（對應 receivingOrderId）
}
```
> 欄位3（真實成本）為動態計算欄位，不需要存資料庫（每次查詢時即時用 H01+H02金額 + 該進貨單關聯的 K01/K02 包裝明細加總 ÷ H02重量 算出，2026-07-04 更正：K04 已改歸 SALES_ORDER，不再計入此欄位）。

## 五、已確認決定（2026-06-29）

1. **`receivingOrderId` 掛在 `PackagingOrder`（主單）層級**，跟現有 `salesOrderId` 同層級寫法一致。
   → 代表一張包裝主單（PackagingOrder）只能整張對應一個進貨單或一個銷售單，不會在同一張主單下混用兩種來源。
2. **「解除鎖定重新計算」要做**：ADMIN 角色可手動解除某張進貨單的成本鎖定狀態，解除後該進貨單的庫存批次成本分析重新回到可編輯/可重新鎖定狀態，需寫 AuditLog。
3. **成品入庫「事後編輯單價」功能保留**：即使入庫單價改為自動帶入鎖定成本，ADMIN/OFFICE 仍可在入庫明細事後手動修改單價（沿用現有編輯權限規則），不影響已鎖定的「庫存批次生產成本」本身（兩者是獨立的數字，編輯入庫單價不會回頭改動進貨單的鎖定成本）。
4. **模組 UI 採獨立卡片**：「庫存批次生產成本分析」在作業系統選單裡獨立一張卡片，跟進貨、加工、包裝、運輸、銷售、採購、監控平等並列，不掛在監控模組底下。

## 六、Phase 規劃建議（依專案開發規則，不可一次全部生成）

```
Phase A：Schema migration（PackagingItem.applicableTo、PackagingDetail.receivingOrderId、
          ReceivingOrder 新增成本鎖定欄位）
Phase B：庫存批次生產成本分析模組（新增，含鎖定功能）
Phase C：包裝模組改版（PackagingItem 新增欄位 + PackagingCreateForm 依類型導引）
Phase D：成品入庫簡化（移除手動單價，改自動帶入鎖定成本）
Phase E：銷售單成本分析改版（移除進貨單追溯邏輯，改用入庫鎖定成本 × 銷售數量）
Phase F：舊資料處理（決定要不要補 migration script 算出舊入庫明細的單位成本）
```
