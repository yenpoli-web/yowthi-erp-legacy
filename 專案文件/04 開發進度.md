|add_inventory_contract_order|ContractWorkOrder.inventoryDone；InventoryContractOrder 關聯表|

### 核心業務邏輯（已鎖定）

**商品分類**
```
EXPORT → H02 出口成品（籃子/箱子）金額 = 重量 × 數量 × 單價
DOMESTIC → H03 境內成品（RE）金額 = 數量 × 單價
```

**庫存流程**
```
進貨（S-）→ 加工（PO-）→ 成品入庫（I-）→ 銷售（O-）
代工（C-）→ 成品入庫（I-，獨立單據）→ 銷售（O-）
現有庫存 = Σ入庫數量 - Σ銷售數量（SalesInventoryDetail.quantity）
```

**salesStatus 自動判定**
```
關聯後：soldQty >= 入庫數量 → DONE；否則 → IN_SALES
移除後：soldQty = 0 → NONE；soldQty > 0 → IN_SALES
選單只顯示 NONE 和 IN_SALES，排除 DONE
```

**SalesInventoryDetail.quantity**
```
= 銷售明細中對應 productId 的 quantity（件數），非整批入庫數量
```

## Phase 6.5：加工系統秤重計算改造 ✅ 已完成（2026-06-17~19）

H01（原料加工）與 H02（成品加工）的數量輸入方式全面改為「秤重量 + 籃子數」輸入，前端即時計算实重，ADMIN 介面（ProcessingCreateForm.vue）與 GUIDED 介面（GuidedView.vue）同步修改。

**H01 欄位順序：**
```
1. 取用量欄：秤重量 + 大籃子數(1.1kg/個) → 取用量 = 秤重量 - (大籃子數 × 1.1)
2. 完成品欄：秤重量 + 小籃子數(2.5kg/個) → 完成品 = 秤重量 - (小籃子數 × 2.5)
3. 瑕疵品欄：秤重量 + 大籃子數(1.1kg/個) → 瑕疵品 = 秤重量 - (大籃子數 × 1.1)
4. 工資率
```

**H02 欄位順序：**
```
1. 完成品欄：秤重量 + 小籃子數(2.5kg/個) → 完成品 = 秤重量 - (小籃子數 × 2.5)
2. 工資率（移除廢料欄）
```

H03 保持原樣（直接輸入 outputQty + wasteQty + wageRate）。

**附加細節：**
- 籃子數欄位預設值：輸入秤重量後，若籃子數欄為空，自動填入預設值（大籃預設 1、小籃預設 4），仍可手動修改
- 籃子數欄位只接受整數，秤重量欄位接受小數一位
- inputQty 存入後端為計算後的取用量（H01）或完成品量（H02）
- Step 5 重整为固定不可捲動佈局（鍵盤固定底部，上方區塊可捲動），適用於 ADMIN 與 GUIDED 兩介面

## Phase 6.7：全系統硬刪修復 ✅ 已完成（2026-06-19）

**關鍵發現：** 9 個 master-data controller 使用 `@HttpCode(HttpStatus.NO_CONTENT)` 強制回傳 204，導致成功/失敗訊息均被吞掉，是「硬刪失效」的根本原因。

**修復內容：**
```
1. 全系統 26 個 hardDelete 函式（9 個 master-data + 17 個作業系統模組）
   補上 P2003/P2014 外鍵約束錯誤處理，轉為 HTTP 409 ConflictException
2. 9 個 master-data controller 移除 @HttpCode(NO_CONTENT)，
   統一回傳 200 + { success, deletedId }
3. 27 個前端檔案修正錯誤訊息顯示，改由 e?.response?.data?.message 讀取後端
   真實錯誤原因，不再只顯示固定的「刪除失敗」
4. 修復入庫單(InventoryOrder)/入庫明細(InventoryDetail)/代工單(ContractWorkOrder)
   硬刪時遺漏刪除 inventoryContractOrder 與 salesInventoryDetail 關聯表的問題
```

**影響範圍：** 代工管理、成品入庫、商品管理三大模組的硬刪失效問題已修復。

### 成本分析（最終版設計，經歷幾輪重設）

**最終架構**：以「銷售單」為主軸，人工選取要分析的銷售單（出口/境內各自多選，日期區間僅用于筩選候選單据），再沿著 S→PO→P/C→I→O 關聯鎖追溯計算。

```
出口：毛利 = 銷售金額 + 庫存金額 − 進貨總額 − 加工總額(H01+H02) − 包裝費 − 代工總額
境內：毛利 = 銷售金額 − 包裝費
```

- 各項成本透過 `SalesInventoryDetail→InventoryDetail→InventoryOrder→InventoryReceivingOrder/InventoryContractOrder` 鎖追溯取得，**去重**但**不按數量比例分摊**（同一批被不同次查詢另外選中時不會自動計算重複，需使用者自行注意選取範圍）
- 庫存金額 = 查詢期間內入庫且尚未售出部分 × 重量 × 入庫單價（每個 InventoryDetail 僅計一次）
- 加工總額僅計 H01+H02（境內 H03 不計入出口成本，其本身也不另外計加工費）
- 包裝費透過 PackagingOrder.salesOrderId 直接關聯取得
- 同療批入庫如果從未被任何銷售單關聯（完全未售），根據設計不會出現在查詢結果中（需透過選取到实際關聯該批入庫的銷售單才能追溯到），属於模型邊界情況，不是 bug
- 套用同一套共用 PDF 匯出工具，可匯出出口/境內各自明細+合計毛利

**設計決定變遷記錄**：本主題全期連續重設三次才定案（期間制進貨/加工/包裝/未售庫存 → 出口/境內分組期間制 → 以銷售單為主軸的真实追溯制），最終版本為上述追溯制。

## Phase 9.x：上線後持續修正 + 部署機制重建 ✅ 已完成（2026-06-26）

本期分烨兩部分：(A) 業務邏輯 bug 修正，(B) 發現部署流程本質性漏洞後，全面重建 VPS 部署機制。

### (A) 業務邏輯 Bug 修正清单

#### Fix 1：補登加工明細被錯誤導向到今日自動建立的加工單
`ProcessingCreateForm.vue` submit() 原本透過中間變數 `existingOrderId` 間接取得 orderId，改為補登模式（`props.targetOrder` 有值）時強制直接使用 `props.targetOrder.id`，絕对不經任何中間變數，彻底排除落入 `findOrCreateOrder`（今日自動尋找/建立）邏輯的可能性。

#### Fix 2：加工管理同員工連續新增明細（跳過重選員工）
参考包装管理模式，新增 `savedOrderId` 状態，儲存成功後原地顯示「繼續新增（同一員工）/ 已完成」，選「繼續」時保留 employeeId/receivingItemId/targetOrder，只重置加工類型相關欄位，跳回 Step 3。

#### Fix 3：成品入庫代工来源重量公式修正
`InventoryCreateForm.vue` `toggleContract()` 原本用「代工單實際過磼總重量÷數量」推算單件重量（算出 0.4kg 的錯誤值），改為直接依 Product.unitWeight 帶入，與進貨來源逻輯一致；`onMounted` 調整為先 loadProducts() 再 loadReceivingOrders()。

#### Fix 4：成品入庫明細抽屬「總數量」標籤用錯 i18n key
`InventoryDetailDrawer.vue` 統計欄套用 `t('totalQty')`（「總重量」語意，適用於進貨模組），但入庫「數量」是件數不是重量，改為 `t('totalQtyLabel')`。

#### Fix 5：銷售單「總重量」其实是這錯誤加總，改為「總數量」
`SalesDetailDrawer.vue`、`SalesListView.vue` 原 `totalWeight` 計算是將每筆明細「單件重量」直接加總（不乘數量），既不是真正總重量亦與標籤不符，改為 `totalQty`（加總 quantity），標籤改 `totalQtyLabel`。

#### Fix 6：銷售單綁定同商品多筆入庫明細時 500 錯誤 → 改為 FIFO 多批次扣減
**原因**：`addInventoryDetails()` 不論選了幾筆都用「銷售明細總數量」套用到每筆，同商品選兩筆時各自被塞入全額數量，超出個別可用庫存並且抹用普通 500 錯誤。重寫為 **FIFO 多批次扣減**（按商品分組，每組依建立時間由舊到新依序扣，扣到歸零→DONE，未歸零→IN_SALES，輪不到的不建立關聯），並改用 `ConflictException`（409）取代普通 Error。`updateDetail()` 中舊版「自動同步入庫關聯」邏輯與新 FIFO 模式衝突，已移除。

#### Fix 7：H02 完成品加工查詢完成比例拆為兩個独立欄位
原 `completionRate`（H02÷H01）拆成 `h01CompletionRate` 與 `h02CompletionRate`，都以「總重量」為分母。梚出部署未重新 build 的隱藏问題（見下方 B）。

### 新增設計：包装項目工資率自動帶入
`PackagingItem` 新增 `wageRate Decimal? @db.Decimal(12,2)`（手動 SQL migration）。包装管理選取包装項目時，若該項目設定過工資率則自動帶入（仍可修改），未設定則留空手動輸入。

### 新增設計：入庫/包装「已完成銷售存放區」
ContractWorkOrder 與 PackagingOrder 新增 `salesDone Boolean @default(false)`。入庫單關聯的進貨批次+代工單全部被標記銷售完成時，自動從主畫面移入存放區（不刪除）；包装單本身有独立標記按鈕。

**現象**：偶爾登入會卡在「登入中」不回應，必須整理頁面才能恢復，PWA 模式下無網址列無法整理。本機開發環境不會發生，只在 VPS 正式環境出現。

**排查過程**：
1. 檢查後端 `auth.service.ts`，確認 bcrypt.compare 為非同步版本（不會阻塞事件迴圈），排除後端阻塞可能性
2. 發現全系統 axios 請求完全沒有設定逾時時間（timeout），任何網路異常都可能造成 Promise 永遠不 resolve/reject → **修正：`axios.defaults.timeout = 15000`**，並在 `LoginView.vue` 補上逾時情境的友善錯誤訊息（th/zh-TW 新增 `login.error.timeout`）

6. 實測驗證：第一次開啟未套用新版本（不打斷當下操作），第二次重新開啟才正式更新，符合預期行為

### (G) Nginx `/uploads/` 靜態資源代理缺失（圖片破圖問題）

**現象**：員工/農民等基本資料模組上傳的照片，本機開發環境顯示正常，但 VPS 正式環境上傳新照片後一律顯示破圖示。

**排查過程**：
1. 一開始誤判為「VPS 部署機制重建（2026-06-26）時遺失正式環境舊照片檔案」，但使用者確認舊資料原本就沒有上傳過照片，這是全新上傳的照片才會壞，排除此假設
2. 確認後端 `backend/public/uploads/` 目錄確實有正確寫入剛上傳的圖片檔案（`ls` 確認檔案存在、時間吻合），排除後端儲存問題
3. 調閱 VPS Nginx 設定檔，發現 443 (HTTPS) server block 只有 `/api/` 會 proxy_pass 到 NestJS backend (`http://127.0.0.1:3000/`)，其餘所有路徑（包含 `/uploads/`）都落入 SPA fallback 規則（`try_files $uri /index.html`）
4. **根本原因確認**：`/uploads/` 從建站以來就沒有設定任何轉發規則，瀏覽器請求圖片時實際拿到的是前端 `index.html`，自然顯示為破圖。本機開發環境用 vite dev server，本身就有 proxy 設定轉發 `/uploads` 到 backend，所以本機一直正常，掩蓋了 VPS 端這個設定缺失

**修正**：在 Nginx 設定檔的 `/api/` 規則之前（必須在 SPA fallback 規則之前）新增：
```nginx
location /uploads/ {
    proxy_pass http://127.0.0.1:3000/uploads/;
}
```
跑 `nginx -t` 驗證語法、`systemctl reload nginx` 套用（不需重啟整個服務）。實測驗證：重新整理頁面後，原本破圖的照片正常顯示。

**Schema 變更**：無（純 VPS 基礎設施設定，不涉及程式碼或資料庫）

## Phase 8.x：庫存批次生產成本分析（鎖定單位成本架構，取代追溯認列制） ✅ 已完成（2026-06-29 ~ 2026-06-30）

### 背景：為何放棄舊版「銷售單追溯進貨單」成本分析

舊版成本分析（2026-06-22 定案、2026-06-28 微調）採「銷售單事後追溯進貨單」設計，搭配 `cost_claims` 認列表處理重複計算問題。實測發現該機制存在無法修補的根本性矛盾：

- 同一張進貨單若被多張銷售單分批共用，**合併查詢**（同時選兩張銷售單）會把該進貨單的認列範圍正確擴大為「兩者皆有關」；但事後**單獨重查**其中一張銷售單時，系統會判定該進貨單「已被其他組合認列」而排除，導致同一張單獨查詢兩次得到不同結果（先查是 36,000，做過合併查詢後再單獨查變成 0）
- 這不是 bug，是「先到先得、且隨查詢範圍擴大而鎖定」這種認列模式的數學必然結果：**不可能同時滿足「任何單獨查詢結果都一致」與「合併查詢不重複計算」兩個需求**，只有「比例分攤的單位成本法」能同時滿足兩者
- 結論：改為在**入庫批次成立的那一刻**就把成本鎖定成單位成本（每公斤），銷售單只需要「數量 × weight × 鎖定單價」，不再需要任何事後追溯或認列機制

### 中途發現的缺口：代工（ContractWork）入庫完全沒有鎖定成本機制

```prisma
model ContractWorkDetail {
  costLocked    Boolean   @default(false)
  costUnitPrice Decimal?  @db.Decimal(12,2)  // = amount ÷ (quantity × weight)，鎖定當下計算並存
  costLockedAt  DateTime?
  costLockedBy  Int?
}
```

與進貨單機制的關鍵差異：代工明細本身已是成品（不需經過H01/H02加工），**以「代工明細」為單位**直接算 `amount÷(quantity×weight)`，不需要像進貨單那樣聚合加工金額，也**不需要**預估包裝成本欄位（沒有籃子/箱子數量輸入步驟）。入庫流程（H02代工來源）同步比照進貨單邏輯：只能選「明細已鎖定成本」的代工單，單價自動帶入且唯讀。

## Phase 8.x：成本分析真實成本與毛利公式修正 ✅ 已完成（2026-07-27）

### 問題原因

原出口成本分析直接使用 `InventoryDetail.unitPrice`，以
`Math.floor(銷售數量 × 每件公斤數 × 入庫單價)` 計算，沒有依來源進貨單即時納入總進貨金額、
H01、H02、K01/K02 工資，也沒有把自產與代工分列，造成「真實成本」及毛利嚴重失真。

### 正式修正

```text
每張來源進貨單真實單位成本
= ROUND(
    (總進貨金額 + H01工資 + H02工資 + K01/K02工資)
    ÷ Σ(關聯出口入庫明細數量 × 入庫每件公斤數),
    2
  )

自產真實成本
= Σ ROUND(銷售關聯數量 × 入庫每件公斤數 × 來源進貨單真實單位成本, 2)

代工成本
= Σ ROUND(銷售關聯數量 × 入庫每件公斤數 × 代工鎖定單位成本, 2)

毛利
= ROUND(總銷售金額 − 自產真實成本 − 代工成本 − 非K01/K02包裝費, 2)
```

- 成本池固定以每張 `ReceivingOrder`／品項分開計算，來源日期為 `ReceivingOrder.orderDate`。
- K01/K02 依 `PackagingItem.applicableTo = RECEIVING_ORDER` 納入來源真實成本；銷售端僅再扣
  `applicableTo = SALES_ORDER` 的 K03/K04，避免重複。
- 代工批次透過 `SalesInventoryDetail` 的鎖定每公斤成本，按各銷售單實際使用數量與重量分攤。
- 出口查詢全程純讀取，不建立 `CostClaim`，不修改既有交易與成本資料。
- 若入庫單缺少成本來源、同時混有進貨與代工來源，或進貨來源沒有有效出口入庫總公斤數，回傳
  409 並要求先修正來源資料，不自行猜測成本。
- 前端與 PDF 新增「代工成本」欄位，所有成本分析金額固定顯示小數 2 位。

## Phase 9.x：手機連續點擊／輸入造成畫面放大修復 ✅ 已完成（2026-07-27）

### 問題原因

手機瀏覽器會把快速連續點擊同一按鈕或數字鍵判定為雙擊縮放；iPhone 對字級小於 16px 的原生輸入框，
在聚焦時也會自動放大頁面。原全域樣式沒有定義觸控手勢規則，數字鍵盤亦未禁止雙擊縮放。

### 修正內容

- `html`、`body`、`#app` 與所有互動元件套用 `touch-action: manipulation`，阻止雙擊放大，同時保留
  單指捲動與使用者主動雙指縮放。
- `NumericInputModal` 數字鍵另外套用 `touch-action: manipulation`、`user-select: none`，連續輸入
  相同數字不再觸發縮放或文字選取。
- 手機／觸控裝置的原生 `input`、`textarea`、`select` 強制至少 16px，避免 iPhone 聚焦自動放大。
- 不修改 viewport 為 `user-scalable=no`，保留無障礙縮放能力。

### 驗證

- Vue／TypeScript／Vite production build 通過。
- 以 390×844 手機 viewport 驗證：根節點、互動元件 `touch-action = manipulation`，輸入框 16px。

## Phase 9.x：銷售明細與入庫關聯修改防護 ✅ 已完成（2026-07-27）

### 問題原因

銷售明細採多批次 FIFO 入庫分配後，`updateDetail()` 不再自動改寫 `SalesInventoryDetail`，但前後端仍允許
直接修改已關聯商品的數量。實測將 L01 從 70 籃改成 50 籃時，銷售金額減少 20 籃，但入庫關聯仍扣
70 籃，造成銷售收入、真實成本與現有庫存失去一致性。

### 正式操作規則

```text
移除該商品全部入庫明細關聯
→ 系統重新計算 InventoryDetail.salesStatus 與剩餘庫存
→ 修改商品／每件重量／銷售數量
→ 重新選取入庫明細
→ 系統重新執行 FIFO 分配
```

- 已有入庫關聯時，後端以 409 阻擋商品、重量、數量變更及銷售明細軟／硬刪除。
- 單價只影響銷售收入，仍可直接修改。
- 前端鎖定商品、重量、數量欄位，並提示先移除下方入庫關聯；刪除操作亦先行阻擋。
- 保留既有 `removeSalesInventoryDetail()` 邏輯：移除關聯後依剩餘已售量更新 `NONE`／`IN_SALES`／`DONE`。

### Prisma Schema 變更

無。本次只增加既有 FIFO 作業順序的前後端防護、測試與文件，不執行 migration 或自動修改交易資料。
